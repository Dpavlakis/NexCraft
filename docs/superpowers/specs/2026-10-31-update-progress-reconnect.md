# Update progress after navigation — 2026-10-31

The user reports that starting a modpack update, closing/leaving its screen, and returning hides progress and enables Update even though the existing daemon task continues in the console. Component-local task tracking is cleared on unmount; the current task-status API requires an ID the remounted screen no longer knows.

On opening/reopening, changing target and refreshing the Update screen, perform a read-only authoritative lookup of the current instance's running update, independently of slow version/changelog loads. Reattach to the same task through existing guarded non-overlapping polling, show its real phase/progress and disable Update/version selection while checking or running. Reopening must not submit another update, restart a task, or show another started notification. Success refreshes installed metadata once for the correct current target. A genuine no-task result restores idle behavior; lookup errors must not be mistaken for idle or successful completion and provide the existing Refresh retry.

Backend contract: admin-only GET /api/protected_modpack/active_task with daemonId/uuid (same permission as update), proxying modpack/active_task with instanceUuid. Return the existing task-status shape or null when a valid current instance has no relevant running task. Only exact current-instance ModpackUpdateTask or existing-instance Bedrock preserve-world ModpackInstallTask may match. Exclude unrelated types, initial installs, terminal tasks and different instances. Lookup never schedules/cancels work or exposes all tasks. Existing opaque-ID task_status remains compatible.

Preserve instance/daemon/generation fences, unmount cancellation of local polling only, duplicate-click protection, failure semantics, version-cache/changelog behavior and existing permissions. No blanket limits, local-storage-only authority, durable task journaling or daemon-restart recovery is introduced. The source of truth is the running daemon task.
